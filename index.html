Migration plan

Three phases. No risky switch day.

Click a phase to see how traffic moves. The whole point is that there is never a moment where members can miss a class reminder or a payment alert.

PHASE 1

Add FCM next to OneSignal

The app registers with FCM on the Firebase project that already exists. OneSignal keeps doing all the work. FCM listens quietly and proves itself with test campaigns.

PHASE 2

Shift traffic gradually

Campaigns move to FCM step by step, per club and per campaign type. The router blocks any duplicate. If anything looks off, one flag moves traffic back in seconds.

PHASE 3

FCM carries everything

OneSignal can stay as a paused backup or be removed later. Push cost drops to zero because FCM is free at any volume. Nothing about this step is urgent, it happens when the data says it is safe.

Architecture

How both SDKs live in one app without fighting.

The tricky part of this job is not adding FCM. It is making sure two delivery paths never collide. On Android both systems want the messaging service. On iOS both want the APNs device token. Here is the exact plan for each platform.

🤖 Android (Java)

Push arrives at the deviceFrom the OneSignal channel or straight from FCM. Both ride Google Play services underneath.
↓
Single FirebaseMessagingService entry pointOnly one service can own incoming messages. Ours does, and it hands OneSignal payloads to the OneSignal SDK so nothing existing breaks.
↓
Routing layer with a dispatch idEvery campaign carries one shared id. First arrival wins, the second is dropped silently. Member sees exactly one notification.
↓
OneSignal pathUntouched. Same channels, same deep links, same behavior members know.
FCM pathNew. Same notification channels and deep links, so both paths look identical to the member.

🍎 iOS (Swift)

APNs delivers the pushApple is always the real carrier on iOS. OneSignal and FCM are both senders that go through APNs.
↓
One APNs token, shared safelyThe app registers once. The token is handed to OneSignal exactly like today, and also mapped to FCM on the existing Firebase project.
↓
Dedup with apns-collapse-idBoth senders stamp the same collapse id per campaign. If both arrive, iOS replaces the first with the second, so the member always sees exactly one banner. This is Apple's own documented mechanism, not a workaround.
↓
OneSignal pathCurrent certificates and setup stay valid. No re-provisioning panic.
FCM pathUses an APNs auth key, which never expires. The yearly certificate renewal chore can finally end.

The four failure points, each with its answer

✓ Service collision on Android
Two SDKs both declare a messaging service. Manifest priority plus a single owned entry point resolves it. This is the bug most attempts ship with.
✓ Duplicate notifications
One campaign, two channels, two banners. On Android the router drops the second arrival by dispatch id. On iOS a shared apns-collapse-id makes the system itself show only one.
✓ Token drift on iOS
APNs token refreshes must reach both systems every time, or one side silently goes deaf. The registration hook updates both in the same call.
✓ Existing Firebase project reuse
The project OneSignal already uses stays untouched. FCM registration is additive. No config file swap, no risk to current delivery.

Built for a fleet

One change, every club app.

When many white label apps share one codebase, a migration is only good if it rolls out everywhere without hand editing each app. This plan is designed for that from day one.

1

Single shared module

The routing layer ships as one module in the shared codebase. Every club app inherits it on its next build, no per app work.

2

Remote controlled rollout

Which channel carries traffic is a server side setting, not a hardcoded value. Move one club, ten clubs, or all of them without touching the stores.

3

Instant rollback

If any club sees a delivery issue, flip its flag back to OneSignal in seconds. No emergency release, no waiting on app review.

4

Delivery report per club

A simple daily count of sent, delivered and suppressed duplicates per club, so the switch is a decision made on data, not on hope.
